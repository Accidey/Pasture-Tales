### 读完 Jade 整条服务端数据链路后确认的机制

1. `WailaTickHandler` → `handler.shouldRequestData(accessor)` 生成 provider 列表，列表来源是**客户端**的
   `WailaCommonRegistration.getEntityNBTProviders()`，且只在 `isTimeElapsed(rateLimiter=250ms)` 时才发包。
2. `RequestEntityPacket` 用 `entityDataProviders.idMapper()` 的**注册顺序整数 ID** 传输 provider 列表。
3. `EntityAccessorImpl.handleRequest` 有 `if (!message.dataProviders().contains(provider)) continue;`
   —— 服务端只执行客户端点名的 provider，这条链「要么全通、要么全断」。
4. **最关键发现**：`ServerPingPacket.handle` 里客户端会用服务端下发的 `entityProviderIds` 调
   `entityDataProviders.remapIds(...)` 覆盖本地 idMapper。若服务端 ID 表与客户端不一致，
   `getIdOrThrow(ourProvider)` 会抛异常 → 请求包编码失败 → 永远不发请求 → 永远「未知」。
5. `ObjectDataCenter.getServerData()` 在 `serverData == null` 或 `verifyData` 失败时返回 null；
   此时 `WailaTickHandler` 会跳过整块请求逻辑，tooltip 仍渲染（Jade 内置信息），但依赖 serverData 的条目全空。
6. `AccessorImpl` 构造函数 `serverData = serverData == null ? new CompoundTag() : serverData.copy()`
   —— 客户端 accessor 拿到的是快照，每 tick 重建。

用户提供完整正式客户端日志 `D:\Games\MINECRAFT\1.21.1\.minecraft\logs\latest.log`，决定性证据在第 182~192 行：

	at WailaClientRegistration.endSession(WailaClientRegistration.java:563)

### 完整因果链

1. `registerClient` 里手动调了 `registration.addConfig(UID, true)`。
2. 但 `ClientRegistrationSession.end()` 第 221 行回放 `registerEntityComponent` 时，
   `WailaClientRegistration.tryAddConfig(provider)` 会**自动**为组件提供者建同名配置条目
   （条件 `!isRequired() && !containsKey(uid)`，默认值取 `enabledByDefault()`）。
3. 第 222 行再添加我们手动那条 → `PluginConfig.addConfig` 的 Preconditions 抛异常。
4. **致命**：`client.endSession()` 抛异常后，`CommonProxy.loadComplete` 里紧随的
   `common.endSession()` **永不执行** → 服务端 `entityDataProviders` 从未回放注册。
5. 于是 provider 不在客户端请求列表里，服务端 `appendServerData` 永不执行。
6. 而第 221 行组件提供者**已经**回放成功 → `appendTooltip` 照常调用 → 显示「未知」。
   —— 这就是为什么「能显示但永远是未知」，极具迷惑性。

### 修复

`AnimalFleeJadePlugin.registerClient` 删掉 `registration.addConfig(...)`，只保留
`registerEntityComponent` + `markAsClientFeature`。**Jade 会自动建配置条目。**

1. **`EntitySpawnReason` 不存在（编译期）**：项目实际编译用的是旧版 `MobSpawnType`！

### ⚠️ 时间基准修正：`gameTime` → `dayTime`（用户环境有时间加速模组）

- 现象：用户加了让 MC 天数加快流逝的模组，但用 `gameTime` 计数仍按 1 tick=1 tick 走，
  "0.5~1 天"在加速环境下实际远超游戏内天数。
- 根因：`level.getGameTime()` 是**世界总 tick 数**（固定每 tick +1，不受时间流速影响），
  而 `level.getDayTime()` 是**游戏内昼夜时间**（0~24000 循环，时间加速模组会让它每 tick 涨更多）。
- 修复：全部改用 `getDayTime()` 的**差值**（`(dayTime - start + DAY_LENGTH) % DAY_LENGTH`）判断经过了多少游戏内时间。
  - `FishFeedingHandler` 登记时记录 `startDayTime = level.getDayTime()`，目标 `targetDelta = 12000~24000`。
  - `FishFeedingSavedData` 的 `Entry` 字段改为 `(pos, startDayTime, targetDelta, count)`，
    NBT 键 `StartDayTime` / `TargetDelta` / `Count`。
  - 到期判定：`delta >= targetDelta` 即生成，无论时间流速多快/多慢都对应"游戏内 0.5~1 天"。
- 日志：每秒打印 `delta/targetDelta` 进度，直观显示还剩多少游戏内时间。

## 钓鱼：钓上来的鱼不是物品，而是实体（参考 Fishing-Real-master）

### 需求变化
- 之前：钓上一条鱼 → 附近鱼实体随机移除。
- 现在：钓上来的鱼**不是物品**，而是把被扣掉的那条鱼实体**拉到玩家脚边**，玩家要亲手杀鱼才能得到物品。
- 参考：`D:\Games\MOD\牧业\Fishing-Real-master`（Fabric+NeoForge 双端模组）。

### Fishing-Real 的实现（已读源码）
- `FishingRealNeoforge.onItemFished` 监听 `ItemFishedEvent`，遍历 `event.getDrops()`：
  用数据包注册表把鱼物品 → 鱼实体，`fishUpEntity` 把实体放在鱼漂位置并**以抛物线速度抛向玩家**。
- 关键 API：`event.getHookEntity()`（不是 getHook）、`player.awardStat(Stats.FISH_CAUGHT, 1)`、
  `CriteriaTriggers.FISHING_ROD_HOOKED.trigger(...)`。

### 我的实现（`FishConsumptionHandler` 重写）
- `pickFishNearby` 从附近 16 格选一条存活 `AbstractFish`（不删除）。
- `pullFishToPlayer`：把鱼实体 setPos 到鱼漂位置，设置朝玩家的速度
  （`toPlayer * 0.12`，垂直方向额外加 `sqrt(sqrt(lenSqr)) * 0.18`），与 Fishing-Real 一致。
- 过滤掉落：`event.getDrops()` 中所有 `stack.is(ItemTags.FISHES)` 的物品 `setCount(0)`（不生成物品实体）。
- 手动补统计：`awardStat(FISH_CAUGHT, 1)` + `FISHING_ROD_HOOKED.trigger(...)`。
- `FishPopulationHandler.removeOneFishNearby` 已删除（不再有调用者）。

### 性能优化（重要）
- 原 mixin 每 tick 做 BFS+实体扫描，太贵。
- 改为 `@Unique` 常量 + **persistentData 缓存**：每 20 tick 重算一次，
  缓存 key `animalflee_legal_water` / `animalflee_legal_tick`，其余 tick 直接读缓存。
- 注意：mixin 的 static 方法无法用实例字段缓存，用 `hook.getPersistentData()` 存（FishingHook 是 Entity，有 persistentData）。

### 标签判定（天然兼容任意模组的鱼）
- 鱼物品：`ItemTags.FISHES`（`minecraft:fishes`）。
- 鱼实体：`AbstractFish` 类（含 Cod/Salmon/TropicalFish/Pufferfish 及所有继承子类）。
- 不需要数据包、不需要手写列表，自动识别其它模组加的鱼。

## Mixin 钓鱼限制：仅自然水域可钓鱼（`FishingRestrictionMixin`）

### 需求

- 玩家自己的小坑/人造水池无论钓多久都钓不到鱼；必须在河流、湖泊、海洋生物群系才能钓到。
- 配置开关，默认开启。

### 实现

- **注入点**：`FishingHook.catchingFish(BlockPos)` 的 `@At("HEAD")` + `cancellable=true`。
  该方法只在服务端每 tick 被调用，是「是否上鱼」的唯一决策点；取消它鱼漂永不咬钩、收竿无战利品。
- **自然水域判定**（`isNaturalWater`）：
  1. `level.canSeeSky(pos.above())` —— 必须露天；
  2. 群系快捷通过：`getBiome(pos).is(IS_RIVER) || .is(IS_OCEAN) || .is(IS_BEACH)`；
  3. 否则做**水平 4 连通洪水填充**统计源水方块数量（上限 1024 防卡服），
     达到 `fishingMinWaterVolume`（默认 64）视为自然湖泊。
- 1.21.1 没有独立「湖泊」生物群系，用「连通水面 ≥ 64」近似自然湖泊，比纯群系更符合直觉。
- 配置项（中英文注释块风格）：
  - `fishingRequiresNaturalWater`（bool，默认 true）
  - `fishingMinWaterVolume`（int，默认 64，范围 16~1024）
- 新增 Mixin 基础设施：
  - `src/main/resources/animalflee.mixins.json`（`required:true`，`defaultRequire:1`，package=`com.xulai.animalflee.mixin`）
  - `neoforge.mods.toml` 启用 `[[mixins]] config="${mod_id}.mixins.json"`
  - `build.gradle` 无需改动：NeoForge userdev 7.1.38 内置 mixin 依赖与 AP（refmap）支持。
- BFS 注意：**必须是水平 4 连通**（east/west/north/south），不能用 `current.below().neighbors()`，
  那会变成 3D 体积统计（会把深坑也算进去）。

### 编译自检

- mixin 目标方法 `catchingFish(BlockPos)` 已从 transformed 源码确认存在，签名匹配。
- `defaultRequire:1` 保证若注入点不存在，启动即报错而不是静默失效。
- **⚠️ 已修复的编译错误**：`FluidTags` 在 1.21.1 位于 **`net.minecraft.tags.FluidTags`**，
  不在 `net.minecraft.world.level.material`。反编译的 `FishingHook.java` 第 22 行就是
  `import net.minecraft.tags.FluidTags;`。这是一个容易踩的包迁移坑。

### 来源与结构

- boids-1.21 位于 `D:\Games\MOD\牧业\boids-1.21`，是 **Fabric 模组**（入口 `net.fabricmc.api.ModInitializer`，
  Mixin 注入 `Mob.serverAiStep` 并 `ci.cancel()` 完全接管生物）。我们无法直接用，只移植其**纯算法**。
- 核心算法 `BoidsSimulation`（separation/alignment/cohesion + Gaussian 随机）与 `NearbyMobTracker`
  （40 tick 缓存同类型邻居）原样移植到 `com.xulai.animalflee.logic.boid` 包，改造为静态工具。
- 因为 NeoForge 没有 `serverAiStep` 的 `ci.cancel()` 那种「可取消+返回」，融合方式改为
  **把群聚转向作为逃跑水平速度的扰动叠加**，而非完全接管移动。

### 集成设计（`MobFleeLogic`）

- 新常量：`FLOCK_RECALC_INTERVAL=10`（转向向量每 10 tick 重算）、`FLOCK_SEARCH_RANGE=6.0`、
  `FLOCK_INFLUENCE=0.45`（转向权重）、`FLOCK_CONTRARY_FACTOR=0.25`（方向相反时大幅削弱）、
  `PANIC_FLOCK`（BoidsSimulation 参数，对齐影响放大、聚合影响减小，适合逃跑恐慌）。
- 新 NBT：`AF_FlockX` / `AF_FlockZ` / `AF_FlockTick`，`processFlee` 初始化，`stopFlee` 清理。
- `applyFlockSteering`：
  1. 每 10 tick 用 `NearbyMobTracker.sameTypeWithin(mob, 6.0)` 收集同类，跑 `PANIC_FLOCK.apply` 得转向向量，存 NBT；
  2. 归一化后用点积判断转向与逃跑方向的关系：**同向 0.45 权重，反向仅 0.25**——保证逃跑始终优先；
  3. 合成后限幅到 `speed * 1.25`，防止群聚力把速度拉到离谱。
- 配置：新增 `Config.FLOCK_FLEE`（默认 true），中英文注释块风格与其他配置一致。

### 关键经验

- Fabric 的「取消原版 AI 步进」在 NeoForge 上没有等价物，强行 `ci.cancel()` 会连 `serverAiStep` 的原版逻辑
  （寻路、目标选择）全部杀掉。**叠加扰动** 是跨加载器移植 boids 的正确姿势。

## 修复「动物在水下逃跑」（`MobFleeLogic.java`）—— 含一次回归与最终方案

### ⚠️ 第一版引入的回归（已修）

- 第一版用 `isStrandedInWater(mob)`（`mob.isInWater() && !isAquatic(mob)`）作为「不逃跑」条件。
- **错误**：动物浮到水面后 `isInWater()` 仍然为 true（碰撞箱仍与水相交），
  于是被永久判定为落水 → `shouldFlee` / `processFlee` 全部拦截 → 「浮上来后在水面上不会逃离玩家」。
- 教训：**`isInWater()` 不能区分「没顶」和「漂在水面」**，必须用眼睛高度判断。

### 最终方案：区分「淹没」与「漂浮」

- 新增 `isSubmerged(Mob) = isStrandedInWater(mob) && isHeadUnderWater(mob)`。
- 只有 **完全没顶** 才不逃跑并强制上浮（`tickFlee` 里 `setDeltaMovement(0, SWIM_UP_SPEED, 0)` 后 return）。
- **漂在水面 / 已上岸 → 照常逃跑**。`shouldFlee`、`processFlee` 的拦截条件也一并改为 `isSubmerged`。

### 水面移动手感三处调整

1. 速度打折：`inWater` 时 `speed *= SWIM_SPEED_FACTOR(0.6)`，
   因为手动 `move(MoverType.SELF, ...)` 不走 `LivingEntity#travel()`，没有原版水阻，不打折会像在水面滑行。
2. 浮力替代重力：`inWater` 时 y 速度 `vy * 0.8` 阻尼衰减到 0；陆地才 `-0.08`。
   否则每 tick 减 0.08 会让动物慢慢下沉 → 没顶 → 上浮，形成上下抖动。
3. 卡住阈值分化：`STUCK_THRESHOLD_LAND = 0.05`，`STUCK_THRESHOLD_WATER = 0.02`。
   水中移动本来就慢，用陆地阈值会误判为卡住，导致反复改向并很快放弃。

- 现象：动物掉进水里后在水底继续按水平速度逃跑，很滑稽。
- 根因：逃跑用 `setNoAi(true)` 禁用 AI 后，原版的浮水逻辑（`FloatGoal`）一并失效，
  而手动 `move()` 只设置水平速度，y 方向只剩每 tick -0.08 的重力，于是沉底并在水下平移。
- 修复思路：陆生动物一落水就**停止逃跑并强制上浮**，出水后交还原版 AI 让它游上岸。
  - 新增 `isStrandedInWater(Mob)`：`mob.isInWater() && !isAquatic(mob)`（水生生物不受影响）。
  - 新增 `isHeadUnderWater(LivingEntity)`：`level.getFluidState(BlockPos.containing(getEyePosition())).is(FluidTags.WATER)`。
  - `tickFlee` 开头：落水且头在水下 → 每 tick 强制 `setDeltaMovement(0, SWIM_UP_SPEED=0.18, 0)` 并直接 return
    （约 3.6 格/秒，3 格深约 1 秒出水）；头已出水 → `stopFlee()` 恢复原版 AI。
    注意该分支位于 player 判定之前，故玩家跑掉也会继续上浮，不会淹死在水底；
    且 `return` 使 `NBT_FLEE_TICKS` 不累加，不会误触 `MAX_FLEE_TICKS`。
  - `shouldFlee` 与 `processFlee` 各加一道 `isStrandedInWater` 拦截，避免刚出水又被立刻重新触发。
  - 新增 import `net.minecraft.tags.FluidTags`。

## 逃跑手感重做：去掉瞬移 + 大幅提高逃脱距离（`MobFleeLogic.java`）

用户两个诉求：① 卡住时 `setPos` 瞬移跨高度差太突兀；② 动物跑到一半就停，玩家轻松追上。
期望是「现实中的野生动物，惊慌失措，几乎无法靠近」。

### 修复一：删除瞬移自救

- 原逻辑 `mob.setPos(ax + 0.5, landY, az + 0.5)` 能跨越任意高度差，观感突兀。
- 改为：**卡住 8 tick（`STUCK_REPATH_TICKS`）就调 `pickFleeTarget` 换个方向重跑**，
  用新增的 `NBT_FLEE_REPATH_FAILS` 记录连续失败次数，**连续 5 次（`MAX_REPATH_FAILS`）都卡才放弃**。
  一旦成功移动（`movedXZ >= 0.05`）两个计数都归零，所以山地绕行不会被误判为困死。
- 高度差现在交给原版 `MoverType.SELF` 的 stepHeight（约 0.6 格）自然处理，1 格以内自动上去。

### 修复二：停止距离过近

- 原停止条件 `distanceXZ > triggerDist + FLEE_STOP_MARGIN`（10+2=**12 格**），
  且 `needRepath` 分支里只要玩家 > `triggerDist`（10 格）就直接 `stopFlee` —— 动物跑 12 格就停，必然被追上。
- 改为 `safeDistance(triggerDist) = max(32.0, triggerDist * 2.0)`。
  乘 2 是必须的：配置上限可到 64 格，若写死 32 会导致「触发距离 > 安全距离」从而一触发就立刻停止。
- `MAX_FLEE_TICKS` 400 → 1200（20 秒 → 60 秒，仅作死循环保险，正常由距离判定退出）。
- 单次逃跑距离 `FLEE_MIN_DIST/MAX_DIST` 20~35 → 24~40。

### 修复三：惊慌速度（越近越快）

- 新增 `panicSpeed(mob, player, triggerDist)`：玩家在触发距离外为 `PANIC_SPEED_FAR = 0.34`，
  贴脸时线性升到 `PANIC_SPEED_NEAR = 0.48`。
- 参照值：玩家疾跑约 0.28 格/tick，故即使最远处动物仍快过疾跑玩家。

### 已移除

`FLEE_STOP_MARGIN`、`MAX_STUCK_TICKS` 两个常量及全部 `setPos` 调用（grep 确认零残留）。

## 修复逃跑「跑着跑着原地发呆」（`MobFleeLogic.java`）

- 现象：动物逃跑途中突然定住，之后玩家靠近也不再逃。
- **根因：`isEnclosed` 阈值 `ENCLOSE_BLOCKED_DIRS = 3` 太松。**
  该检测原本用于「玩家圈养时不触发逃跑」，但四个方向里只要 3 个方向 4 格内有碰撞箱就判定圈养。
  树林、墙角、复杂地形下极易误判 → `tickFlee` 里 `stopFlee()` → 之后 `processFlee` 开头的
  `isEnclosed` 又把它挡回去 → **永久不再逃跑**，表现为「发呆」。
- 修复一：阈值 `3 → 4`，必须**四面全被挡**才算真正圈养。真正的围栏（四面栅栏）仍能命中，
  三面有树/地形的开阔地不再误判。
- 修复二：新增 `MAX_STUCK_TICKS = 60`（约 3 秒）卡死放弃。原逻辑中自救失败（`landY < 0`）时
  `stuckTicks` 只累加不处理，动物会无限贴墙挣扎。现在累计 60 tick 且仍无法脱困则 `stopFlee` 恢复 AI。
  注意放在 `landY < 0` 的 else 分支内——自救成功会重置计数，正常脱困不受影响。
- 已知局限：`isEnclosed` 是简单启发式，只看 4 个正交方向 × 4 格，无法识别「大围栏中心」
  （动物在 10×10 栏舍正中时四个方向 4 格内都没有栅栏，仍会逃跑）。如需更精准可改判方块类型
  （只认栅栏/墙）或做区域连通性判断。

## 逃跑系统：遇到高1格方块上不去（`MobFleeLogic.java`）
- 用户反馈：逃跑算法遇到高 1 格的方块不会移动上去，要求视觉平滑自然地迈上去。
- 根因：`processFlee` 用 `setNoAi(true)` 禁用了原版 AI，导致 `serverAiStep()` → `jumpControl.tick()` 不再运行，
  `MoveControl` 的自动跳台阶逻辑（`getJumpControl().jump()`）也随之失效；而手动 `setDeltaMovement + move()`
  只走 `Entity.collide()` 的 step-up（默认 `maxUpStep` 0.6），无法跨 1 格完整方块。
- **最终方案（优雅、无跳跃动画）**：逃跑激活时给生物 `Attributes.STEP_HEIGHT` 加瞬态修改器
  `ADD_VALUE +1.0`（id=`animalflee:flee_step_up`），使 `maxUpStep()` 从 0.6 → 1.6，
  原版 `collide()` 的自动跨步直接带生物「走上」1 格台阶（视觉如马跨步，无跳跃）。
  `stopFlee` 时移除修改器。`addTransientModifier` + `removeModifier(ResourceLocation)` 配对。
- 配套放宽：`canEscapeDir` / `isPathClear` / `pickFleeTarget` 的 clearance 计算把
  「头部空 + 台阶高度 ≤ 1.0」视为可通过（`isOneBlockStep` 辅助方法），
  避免 1 格台阶被误判为围栏/堵死导致不触发逃跑或目标点选不到台阶后。
- 关键 API（1.21.1）：`AttributeModifier` 是 record `(ResourceLocation id, double amount, Operation)`；
  `Attributes.STEP_HEIGHT` 是 `Holder<Attribute>`；`LivingEntity.getAttribute(Holder)` 返回 `AttributeInstance`；
  `VoxelShape.max(Direction.Axis.Y)`；`Entity.setYBodyRot(float)` 是 public（`yBodyRot` 字段是 protected，不可直接赋值）。
- 已用 `./gradlew compileJava --offline --no-daemon` 验证编译通过（两次成功；最后一次环境 Gradle 缓存锁被占用，
  但代码只改动了更安全的 `setYBodyRot`）。用户自行编译。

### 诊断过程（关键：一度被 `No refMap loaded` 带偏）
- 初判错误：以为缺 refmap（日志有 `No refMap loaded`、jar 名带 `-srg`），于是加了 `refmap` 字段 +
  `annotationProcessor` + `-AoutRefMapFile`。**这是错的**——NeoForge 1.21.x 用 Mojang 官方映射，
  dev/prod 类名一致，本就不需要 refmap；声明 AP 反而必然报 obfuscation mapping 错（见技能 1、3 节）。
- 用 `javap -v -p` 反查运行期类 `build/neoForm/.../steps/recompile/classes/.../animal/Chicken.class`：
  `aiStep()` 里常量池 `#218 = Methodref #8.#219 // net/minecraft/world/entity/animal/Chicken.spawnAtLocation:(Lnet/minecraft/world/level/ItemLike;)Lnet/minecraft/world/entity/item/ItemEntity;`
  —— **owner 是 `Chicken`，不是声明该方法的父类 `Entity`**。

### 根因
源码写的是 `this.spawnAtLocation(Items.EGG)`，该方法定义在父类 `Entity`、`Chicken` 未重写；
但 **javac 为 `this.方法()` 生成的 `Methodref` owner 用的是 `this` 的静态类型（子类 `Chicken`）**。
原 `@At(target=...)` 用的是 `Lnet/minecraft/world/entity/Entity;spawnAtLocation(...)` → 与字节码对不上 →
`Scanned 0 target(s)` → 注入失败 → 启动崩溃。

### 修复（`ChickenEggLayMixin.java`）
```java
@Redirect(
        method = "aiStep()V",
        at = @At(value = "INVOKE",
                 target = "Lnet/minecraft/world/entity/animal/Chicken;spawnAtLocation(Lnet/minecraft/world/level/ItemLike;)Lnet/minecraft/world/entity/item/ItemEntity;")
)
private ItemEntity animalflee$layEgg(Chicken self, ItemLike item) { ... }
```
两处改动：`method` → `"aiStep()V"`（精确描述符）、target owner `Entity` → `Chicken`。

- `Scanned 0 target(s)` 基本等于 **target 描述符对不上**，别被同行的 `No refMap loaded` 误导。
- `@At(target=...)` 的 owner **永远照 javap 常量池的 `Methodref` owner 原样抄**，
  不要用「方法定义在哪个类」推断；`method` 建议写全描述符 `"xxx()V"`。
- 环境备忘：本沙箱 Bash 缺 coreutils（`ls`/`cd`/`head` 等 command not found）、PowerShell 被沙箱拦截；
  可靠做法是绝对路径调 `javap.exe` 输出到文件再用 Read 读，删文件用 `node -e "fs.unlinkSync(...)"`。

## 🎯 雄性鸡仍显示 Jade「产卵冷却」+ 下蛋计时改走 dayTime（`ChickenEggLayMixin.java`）

### 现象
- 用户：雄性鸡的 Jade 提示框仍显示「产卵冷却」。并且指出「要读取 dayTime，不是 gameTime，因为装了改 dayTime 流速的模组」。

### 根因（Jade 本体自带，不在我们模组里）
- 反汇编 Jade 的 `snownee.jade.addon.vanilla.NextEntityDropProvider`（jar）。
- `appendServerData` 对鸡的逻辑仅有：
  `if (entity instanceof Chicken c) { if (!c.isBaby() && c.eggTime < 48000) tag.putInt("NextEggIn", c.eggTime); }`
  → **完全不看性别**，读的是原版 `Chicken.eggTime`（每 tick 减 1 的 **tick 计数，gameTime 性质**），
    与我们的 `af_next_egg_daytime`（dayTime 制）无关。
- 文案：`jade.nextEgg = 产卵冷却：%s`（zh_cn），由 `appendSeconds` 用 `eggTime / tickRate` 换算秒数。
- 结论：只要 `eggTime < 48000` 且非幼年，任何鸡（含雄性）都会显示这条。

### 无法用 Jade API 精确删除那一行
- `ITooltip` 有 `remove(ResourceLocation uid)`，但**内建 provider 用的是无 UID 的 `add(Component)`**
  （`ITooltip.add(Component)` → `add(Component, null)`，元素 tag 为 null），`Tooltip$Line` 也不带 UID。
  → `remove(null)` 会误删所有无 tag 行，不可用。
- `IWailaClientRegistration` 也没有「注销/隐藏他人 provider」的正规接口（只有 `hideTarget` 隐藏整个目标）。
- 因此只能**从数据源头**让 Jade 不写 `NextEggIn`：即控制 `Chicken.eggTime`。

### 修复（`ChickenEggLayMixin` 重写）
1. 新增 `@Inject(method = "aiStep()V", at = @At("TAIL"))`，每 tick 接管 `eggTime`：
   - 客户端 / 幼年 → 直接返回。
   - 性别缺失（存档加载后 `EntityJoinLevelEvent` 未必触发）→ 兜底调 `GenderLogic.initGender`。
   - **雄性** → `eggTime = Integer.MAX_VALUE`（远超 Jade 的 48000 阈值，Jade 不再写 NextEggIn；原版 `--eggTime` 也永不归零）。
   - **雌性** → `eggTime = clamp(af_next_egg_daytime - getDayTime(), 0, 47999)`：
     **把 tick 计数器改为 dayTime 的镜像**。原版 `--eggTime <= 0` 便恰好在 dayTime 冷却到点时触发，
     于是「加速 dayTime 的模组」下母鸡下蛋频率也随游戏内天数同步（这是用户真正要的）。
     首次遇到未初始化的鸡时写入 `nextEggInterval()`（`dayTime + 24000 + 1000~3000`），保证「最多 1 天一蛋」。
2. `@Redirect` 处理器相应简化：删掉全部 `self.eggTime = getRandom().nextInt(6000)+6000` 赋值
   （这些赋值原本还会被原版紧接着的 `eggTime = random(6000..11999)` 覆盖，属无效代码），
   只保留「是否下蛋 / 受精蛋」判定。

### 关键 API 事实
- `Chicken.eggTime` 是 **public int 字段**（Jade 跨包直接 `getfield` 可证），非持久化（不写 NBT）。
- 原版 `Chicken.aiStep()`：`if (!isClientSide && !isBaby() && !isChickenJockey() && --this.eggTime <= 0) { 播放音效; spawnAtLocation(Items.EGG); eggTime = random.nextInt(6000)+6000; }`
  —— 注意是 `--eggTime` **先自减再比较**，且 spawnAtLocation 之后还会重置一次。
- 项目里**不存在任何 `getGameTime`**（grep 全 src 零命中）；dayTime 制已覆盖 HungerSystem / PregnancySystem /
  EggIncubationHandler / FishFeedingHandler / ChickenEggLayMixin。唯一 tick 制的时长就是原版 `eggTime`，本次已改。

### 遗留 / 待确认
- Jade 那条显示的是「秒」，我们的冷却按游戏内天计（约 1 天 = 24000 dayTime 单位）。
  在加速 dayTime 的世界里数值会随游戏内时间正确下降，但单位仍是「秒」而非「天」——若要更直观需自建 provider（会与 Jade 自带行重复，需先屏蔽原行，目前无正规途径）。
- 未构建（用户一直要求「我自己构建」）。
